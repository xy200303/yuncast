# 07 · 内容策略与轮播方案（混合模式）

> 状态：待评审 · 2026-10-11
> 决策依据：用户拍板——① 走混合模式；② 变体数在场次生成时自行配置；③ 不做"待批准"模式；④ 允许按时间/互动跳场景。

## 1. 结论：混合模式 = 预生成骨架 + 实时插播 + 轮播变体

```
场次（内容包）
 ├─ 知识库范围        本场可用的商品 / 资料文件 / FAQ
 ├─ 剧本场景          场景序列（开场→痛点→讲解→互动→催单→收尾）
 ├─ 生成配置          每场景变体数、语气指令、音色、长度上限
 └─ 轮播方案          场景顺序 + 跳转规则（可多套备选，直播台可切换）
        │
        ▼  一键批量生成（人工可见、可改）
   话术库（本场话术，按 场景 × 变体 组织，已预合成）
        │
        ▼  开播时入池
   话术池 ── 轮播层（normal 车道，变体轮换、循环）
        ▲
        │  插播层（next 车道）：评论回复 / 礼物感谢 / 欢迎 / 冷场自救
    主播 Agent + 触发器 ── 现场生成；可 revise 未播的骨架话术
```

**为什么这样分工**：稳定性不取决于"什么时候生成"，而取决于"有没有经过同一道闸门"。骨架内容事先可见可改，插播内容靠护栏 + 提词器可见 + 急停兜底；两者都进同一个池、过同一道过滤。同时它最接近真主播的工作方式——有脚本，也有现场发挥。

## 2. 三层内容与各自职责

| 层 | 内容 | 生成时机 | 车道 | 风险等级 |
|---|---|---|---|---|
| **骨架** | 剧本场景话术（每场景 N 条变体） | 开播前批量生成、人工过一遍 | normal | 低（事先可见） |
| **插播** | 评论回复、礼物感谢、欢迎、冷场自救、库存/价格修订 | 现场实时 | next / interrupt | 中（护栏 + 可见 + 可急停） |
| **填充** | 冷场暖场短句 | 预置 | filler | 低 |

变体是骨架的关键：同一场景生成多条同义话术，轮播时**不重复同一条**（用完一轮再重洗），解决"循环三遍观众听出来"的重复感。

## 3. 数据模型（草案）

现有表复用：`scripts`（剧本场景）、`live_plans`（场次）、`products` / `knowledge_files`（知识库）、`speech_items`（池）。
新增：

```
live_plans（扩）   新增 persona_id / style_id / bgm / 生成配置（变体数、语气指令、音色）
plan_knowledge     场次 × 知识库范围（product_id / file_id，本场可用集）
utterances         本场话术库：id, plan_id, scene_id, variant_idx, text,
                   voice_id, audio_path, status(pending|ready|failed),
                   source(initial|adopted), created_at
                   —— source 区分"生成时产出"与"复盘采纳的现场改写版"
playlists          轮播方案：id, plan_id, name, active,
                   scenes(json: 顺序 + 每场变体数 + 停留时长上下限), rules(json: 跳转规则)
```

`utterances` 与 `speech_items` 的分工：前者是**场次底稿库**（长期存在、可反复用、可编辑），后者是**本次播出的运行态队列**（有生命周期、播完归档、过程中的改写不回写底稿——见 §5.5）。`speech_items.origin_utterance_id` 记录取件来源，供复盘溯源。开播时按轮播规则从 `utterances` 取件入池。

## 4. 生成流程（场次配置 → 开播）

```
① 场次编辑页
   - 勾选知识库范围（商品 / 资料文件）：支持**全选**与**按标签筛选**（商品多时逐条勾选太累）
   - 选剧本（场景序列）
   - 配置生成参数：每场景变体数（如 3 条）、语气指令、音色、单条长度上限
② 点「生成话术库」→ **生成 Agent 自己调工具取知识**（不是把资料硬塞进 prompt）
     起点：场景目标/要点/禁忌 + 人设 + 演出形式 + 语气指令
     过程：Agent 按需调用工具（见下表），可多轮（search → read → 再 search）
     产出：话术文本数组 + **每条话术的来源引用**（引用了哪个文件/网页）→ 过闸门 → 入库

### 4.1 生成阶段的工具面（Agentic Generation）

生成话术时给 Agent 挂工具，让它自己决定去查什么——比"一次检索后拼 prompt"能多跳、更准，而且工具是可复用的。

| 工具 | 作用 | 生成阶段 | 直播阶段 |
|---|---|---|---|
| `search_knowledge(query)` | 本地知识库检索（商品/资料文件） | ✓ | ✓ |
| `list_products()` / `get_product(id)` | 结构化商品信息（比自由文本可靠） | ✓ | ✓ |
| `read_document(fileId, range?)` | 读已解析的资料全文/分段（PDF/Word/Excel/TXT） | ✓ | ✓（限次） |
| `check_price(product)` | 结构化价格——**价格的唯一来源** | ✓ | ✓ |
| `fetch_url(url)` | 抓网页正文（竞品参数、官网说明、行业资料） | ✓ | ✗ |
| `search_web(query)` | 联网搜索（需搜索 API，可选） | ✓（可选） | ✗ |
| `say` / `insert_next` / `revise_item` | 往池里丢话术 | ✗ | ✓ |
| `advance_scene` / `goto_scene` | 推进/跳转场景 | ✗ | ✓ |
| 话术入库（`save_utterances`） | 写入本场话术库 | ✓（阶段专属） | ✗（改底稿走复盘） |

**按阶段注入工具**（同一个 ToolRegistry，权限不同）：生成阶段能联网、不能进池；直播阶段能进池、不联网（直播时抓网页既慢又有风险）。

### 4.2 三条必须守住的约束

1. **价格与关键事实只能走结构化工具**
   `fetch_url` 抓来的价格、`read_document` 里的旧报价都**不能直接说**——价格一律 `check_price`，产品参数一律 `get_product/search_knowledge`。否则生成时读到的价与直播时报的价会不一致，这是最容易翻车的地方。
2. **来源留痕**
   每条话术记录它引用了哪些来源（`sources: [{type:'file'|'url', id, snippet}]`）——审阅时能看到"这句话是从哪来"，出问题能追溯；采纳/丢弃时也有依据。
3. **成本与轮次上限**
   生成是离线阶段，多轮工具调用可接受，但要设上限：单场工具调用 ≤ 40 次、单次读取 ≤ 8k 字符、单场景生成 ≤ 3 轮工具循环；超限则用已有信息收尾（避免一个场次生成跑十几分钟、烧掉大量 token）。

### 4.3 fetch_url 的安全边界（Guard 的一部分）

| 限制 | 原因 |
|---|---|
| 只允许 http/https | 防 file:// 读取本机 |
| 拒绝内网/本机地址（127.0.0.1、10.x、192.168.x、::1） | 防 SSRF 探测内网服务 |
| 域名白名单（场次级可配，默认常见电商/资讯站） | 减少意外与风险 |
| 单页 ≤ 2MB、超时 ≤ 10s、只取正文文本 | 防大文件与慢站拖死生成 |
| 结果标记为"外部信息，需人工确认" | 外部内容不可信，审阅时高亮 |

③ 生成结果进审阅表格：逐条可编辑 / 删除 / 单条重生成 / 批量重生成某场景；**显示来源引用**（本地文件 / 外部网页分别标注，外部来源高亮提示需确认）
④ 点「预合成」→ 批量 TTS（走语音合成通道；流式开关不影响这里——骨架就是要预合成）
⑤ 开播：按 active 轮播方案把骨架入池（变体轮换），插播层照常工作
```

## 5. 轮播与跳转规则（回答"允许跳场景"）

**默认**：按方案的场景顺序循环；每场内部按变体轮换（同一条不连续播两次）。

**允许的跳转**（四类触发，可叠加）：

| 触发 | 例子 | 实现 |
|---|---|---|
| Agent 判断 | 现场聊到某个话题，主动切到相关场景 | 已有 `advance_scene`，扩为 `goto_scene(sceneId)` |
| 时间规则 | 每个场景最短 3 分钟 / 最长 8 分钟，到点自动推进 | 池内计时 + 触发器（timer.interval） |
| 事件规则 | 库存告急 → 跳「催单」；大量新观众进入 → 跳「欢迎/开场」 | 触发器绑定事件 → 目标场景 |
| 人工 | 直播台点场景卡片直接切 | 操作面板加场景切换（现在禁用态的「切场景」按钮启用） |

**优先级**：插播（next）> 骨架轮播（normal）> 填充（filler）；场景跳转只影响 normal 车道的取件来源，不会打断正在播的条目。


## 5.5 中途改写与底稿沉淀（关键设计）

预生成的话术库只是**初始底稿**，不是冻结内容——直播过程中它会不断被改写。必须分清两个层级：

| 层级 | 存放 | 改写的归属 | 生效范围 |
|---|---|---|---|
| **底稿层** | `utterances`（场次话术库） | 人工审阅、生成、下播复盘采纳 | 本次及以后所有场次（持久） |
| **运行态** | `speech_items`（话术池） | Agent `revise_item`、人工现场改 | 只影响本次播出（用完即弃） |

**默认真理在池**：开播后以池里的内容为准，库不参与运行；池内某条被改写，只改这一条的播出文本（已有 revise 链路：作废旧音频 → 重合成，含竞态守卫）。

### 谁在改、怎么改

| 来源 | 入口 | 层级 |
|---|---|---|
| Agent 现场改写 | `revise_item(itemId, newText)`（已有） | 运行态 |
| 人工现场改某条 | 直播台队列条目 → 行内编辑 → 同一套 revise | 运行态 |
| 人工改底稿 | 场次页话术库审阅表 | 底稿 |
| 下播复盘采纳 | 复盘列表逐条采纳/丢弃（见下） | 运行态 → 底稿 |

### 沉淀策略：回写但隔离（推荐）

现场改写**默认不回写底稿**——否则 LLM 未经监督的改写会无声污染话术库，几次直播后底稿质量就漂移了。改为：

```
直播中：所有改写只进运行态（池），不打断、不弹窗确认
下播后：复盘列表展示"本场改写的条目"
        每条显示：原底稿文本 → 现场改写文本 + 谁改的（agent/人工）+ 为什么（若有）
        人工一键：采纳（覆盖底稿 / 存为新变体）· 丢弃
```

配置项（场次级）：`底稿沉淀策略 = 不沉淀（默认） | 下播复盘采纳 | 自动采纳`。自动采纳只建议给"人工现场改"的来源（人的判断可信），Agent 改写仍走复盘。

### 其它边界

- **正在播的条目不可改**（已有约束，`revise` 拒绝 playing/done）：说出去的话泼出去的水
- **溯源**：池条目记 `origin_utterance_id`，复盘时能建"底稿 → 现场改写"的对应关系（也让"存为新变体"有据可依）
- **改写即新变体**：现场改得好的句子，采纳后可入库成为该场景的新变体——这是"越播越贴合"的正循环
- **改写失败兜底**：改写的重合成失败 → 该条落 failed，池里其它存货继续播；不影响轮播


## 5.6 演出形式（第三层资产）

风格形式既不属于人设，也不属于场次，而是**独立的可复用资产**：

| 层 | 回答 | 内容 | 作用域 |
|---|---|---|---|
| 主播（人设卡） | 我是谁 | 性格、口癖、背景、禁区 + 角色表（姓名与音色） | 跨场次 |
| **演出形式** | **怎么演** | 体裁骨架、语言风格、节奏、角色互动范式 | 跨场次复用，场次引用 |
| 场次 | 这场干什么 | 主题、知识库范围、剧本、引用的人设+形式、话术库、轮播方案 | 单场 |

原则：**换产品不换形式 → 形式是资产；换形式不换人 → 人设是资产；两者组合出"这场怎么播"。**

形式的四类内容（以对口相声为例）：

```
体裁骨架   逗哏抛问题 → 捧哏接茬/抬杠 → 逗哏抖包袱（=产品卖点）→ 捧哏总结 → 循环
语言风格   短句、口语、多用反问与夸张；幽默密度高
节奏       包袱间隔、停顿、语气词
角色互动   谁问谁答、能否互相打断、捧哏的调侃尺度
```

**形式管"怎么说"，剧本管"说什么"**——两者正交，可任意组合（锅具专场 × 对口相声 / × 专业讲解 共用同一套场景与话术库结构）。

内置模板建议：单口带货、对口相声、幽默吐槽、诗歌朗诵、专业讲解、温柔陪伴；支持自定义。

**与 instruction 的分界**：只影响声音表情的（"语气轻松"）放语音合成的 `instruction`；影响文本结构与角色互动的（相声体、朗诵体）放形式。


## 5.7 评论批处理（减少 LLM 调用次数）

**不做"每条评论一次 LLM"，而是攒一批一起给**——成本降一个数量级，且更拟人（真主播也是看完一片弹幕再答）。

### 触发规则（任一满足即派发）

| # | 条件 | 默认 |
|---|---|---|
| ① | 攒满 N 条 | 5 条 |
| ② | 等待窗口 T 秒（从批内第一条到达算起） | 4 秒 |
| ③ | 高优先级直通 | 价格/售后/新粉类**不等批**，单条立即派发 |
| ④ | 池水位告急 | 与评论无关，走补货逻辑 |

①②并行，谁先到算谁 → 最差延迟 T 秒，最好"满 N 立即走"。

### 窗口大小配置在**主播（人设卡）**层

节奏是主播风格的一部分，跟着人设走最自然（同一场次换主播，窗口自动跟着变）：

| 主播风格 | 建议窗口 |
|---|---|
| 快节奏（促销、对口相声） | 2 条 / 2 秒 |
| 中速（标准带货） | 5 条 / 4 秒 |
| 慢节奏（温柔陪伴、专业讲解） | 8 条 / 8 秒 |

全局设置里留"默认值"给未配置的人设卡兜底。

### 边界规则

1. **批量 ≠ 全回**：prompt 明确"从这批里挑值得回的 2-3 条，其余忽略"——否则连回 5 条比逐条还吵
2. **同人合并**：同一观众连发多条合并为一条上下文；**多人问同一问题**合并为"好几个人都在问价格"，回一次即可（顺带解决刷屏）
3. **风暴保护**：待批队列上限默认 50 条，超出按意图优先级丢弃（先丢闲聊，价格/售后/新粉必留）
4. **不进批的事件**：欢迎、礼物感谢等仍走触发器直连（模板零成本零延迟），批处理只处理 `comment.new`
5. **可观测**：每次批次派发记一条事件（批大小、等待时长、挑中哪几条），复盘时用来调窗口——若"总是等满 4 秒才够 2 条"，说明该缩小窗口

## 5.8 话术库治理（变体膨胀与轮换）

| 问题 | 规则 |
|---|---|
| 变体膨胀 | 每场景变体上限 **8 条**，超限提示人工清理；复盘采纳的现场改写版打 `source=adopted` 标记，便于区分与批量清理 |
| 跨场次轮换 | 记变体使用历史，**跨场次弱轮换**（每场随机起点 + 同一条不连续出现）——避免"同一场次开第二次总是同一序列" |
| 直播中切轮播方案 | **下一个取件周期生效**，不打断正在播的条目（与"切场景"同规则） |

## 5.9 常见问题直答缓存（后续优化）

与批处理互补：批处理减少**调用次数**，直答缓存减少**需要过 LLM 的比例**。

```
reply_log 挖掘高频问题 → 人工确认存为「标准问答」→ 命中则直接入池（零 LLM）
                                            → 未命中才进评论批（§5.7）
```

## 6. 闸门（不做待批模式的替代保障）

所有入池内容（骨架 + 插播）统一过滤：

1. 长度上限（单条 ≤ 60-80 字，超出截断或拒绝）
2. 敏感词/违禁词黑名单（可扩）
3. 价格护栏：报价数字只能出自 `check_price` 的返回值，命中"疑似报价但无来源"则拦截并记事件
4. 人设禁区（人设卡里的 taboos 文本匹配）
5. 拦截记 `trigger.dropped` 事件进时间线，便于复盘

## 7. 兜底链

```
骨架轮播中 → 池水位低 → Agent 补货（现场生成，走 next/normal）
           → Agent 不可用 → filler 暖场 → 纯 BGM
骨架生成失败/超时 → 保留上次成功的库 + 允许单条重生成；不影响开播
插播生成失败 → 池内骨架继续，不中断
```

## 8.5 场次 = 开播单元（闭环的最后一环）

**开播动作 = 选场次 → 加载 → 预检 → 启动。** 场次是一次直播的完整快照，主播 Agent 不是全局单例，而是"由场次加载出来"的运行实例。

### 场次里包含什么（完整清单）

| 类别 | 字段 | 说明 |
|---|---|---|
| 身份 | 主题、名称 | 这场播什么 |
| **主播** | `persona_id` | 用哪张人设卡（含角色表 roles） |
| **演出形式** | `style_id` | 怎么说：单口 / 对口相声 / 幽默 / 朗诵 …（见 §5.6） |
| **内容** | `script_id` + 知识库范围 | 剧本场景序列 + 本场可用的商品/资料文件 |
| **话术** | 话术库（`utterances`）+ 轮播方案（`playlists`） | 预生成骨架 + 场景顺序/跳转规则 |
| 声音 | 音色（**覆盖**人设/角色音色）、语气指令、实时/预合成开关、评论批处理窗口 | 本场的语音与节奏口径 |
| 氛围 | **BGM 列表**（多首随机/顺序轮播）与音量、ducking 深度 | 单曲循环一小时会出戏 |
| 自动化 | 触发器启停与参数 | 欢迎/礼物/冷场等 |
| 接入 | **平台选择**（抖音/B站…）+ 对应连接器 + 推流配置（地址/密钥/模式） | 不同场次可能推不同账号/平台；全局设置里的是默认值 |

### 直播台只有一个开播入口：「启动场次」

直播台顶部的场次选择器 + 「启动场次」按钮 = **唯一的开播动作**。原「启动主播」不再是独立入口（主播团页的启动按钮降级为调试用），因为"主播用哪张人设卡"必须由场次决定，而不是全局的"当前人设"。

```
[场次选择器：周五晚锅具专场 ▾]   [▶ 启动场次]        ← 直播台顶部，只有这两个
        │
        ▼ 点一下，按顺序做六件事
① 加载场次配置   写入 activePlanId；本场设置成为当前配置
② 应用身份       把 plan.persona_id 设为当前主播（含角色表）
③ 应用声音氛围   音色、语气指令、实时合成开关、BGM 与音量、ducking
④ 预检           缺失项按阻断/可降级分类，弹一次确认（见下）
⑤ 装载内容       按轮播方案把话术库载入池（骨架就绪，变体轮换）
⑥ 启动 Agent     按"人设 + 演出形式 + 场次 + 剧本场景"组装 system prompt 开会话
```

停止同理：**「停止场次」** = 停 Agent → 池内条目自然播完 → 归档（含场次摘要与改写清单）。

### 预检确认弹窗的内容

点「启动场次」后先跑预检，**阻断项**直接拦住并指路，**警告项**列出来让用户选"继续/先去处理"：

```
✅ 人设：小陶（角色：小陶 / 小助理）
✅ 语音：百炼 qwen3-tts-flash · Cherry · 已测试可用
✅ 话术库：42 条已就绪 / 0 条失败
⚠️ 知识库：本场绑定的「锅具套装」缺少价格  ← 会影响报价
⚠️ 连接器：未连接（将收不到真实评论）
⚠️ 推流：未配置（伴侣模式下只出声，正常）

[ 先去处理 ]  [ 仍然启动 ]
```

### 边界情况

| 情况 | 处理 |
|---|---|
| 没选场次 | 场次选择器提供「自由模式（不加载场次）」——不绑定人设/话术库，纯调试/试麦用；正式使用必须选场次 |
| 场次缺内容（话术库没生成） | 预检列警告，允许启动；此时靠 Agent 现场生成 + 播插层兜底，但会提示"建议先生成话术库" |
| 直播中想换场次 | 不允许直接切；提示"停止当前场次后再启动新的"（结构性变更下一场生效原则的延伸） |
| 部分内容未就绪 | 只装载 ready 的条目；其余保持 pending，等合成完成后自动进轮播 |
| 启动失败 | 停在预检阶段不改动运行态；已应用的配置回滚到启动前的一次快照 |

### 加载场次时发生什么

```
① 写 config.live.activePlanId（重启后仍是这场）
② 把 plan.persona_id 设为当前主播（替代手动"设为当前"）
③ 应用声音/氛围设置（音色、语气指令、BGM）
④ 按 active 轮播方案把话术库载入池（骨架入库、变体轮换就绪）
⑤ 按 plan 启停触发器、应用接入配置
⑥ Agent 会话按"人设 + 形式 + 场次 + 剧本"组装 system prompt 启动
```

**② 是关键**：多张人设卡靠"加载场次"切换，而不是让人手动去人设页点"设为当前"。同理，形式、剧本、话术库都随场次一次性就位——这才是"开播不用重新配置"。

### 音色优先级（四层，后者被前者覆盖）

```
场次指定音色  >  角色音色（编剧模式）  >  人设卡默认音色  >  TTS 默认音色
```

### 运行中改场次绑定的资产：统一规则

| 改动类型 | 生效时机 |
|---|---|
| 结构性资产：人设卡、演出形式、剧本、知识库范围、生成格式 | **下次开播生效**；改动时提示「本场已加载，改动下次生效」，并提供**「立即应用」**按钮（点击才重启 Agent 会话） |
| 运行态热调整：音量、BGM、切场景、插话、修订未播话术、启停单个触发器 | **即时生效** |
| 人工接管期间进来的评论 | 照常进事件队列但**不插播**；恢复后由主播按优先级补回重要类（价格/售后），其余忽略 |

### 预检（Preflight）

加载后、点开播前跑一次检查，缺什么明确说、允许降级开播：

| 检查项 | 缺失后果 | 处理 |
|---|---|---|
| 人设存在且非空 | Agent 无法启动 | 阻断 |
| 剧本有可用场景 | 只能靠插播与补货 | 警告，可继续 |
| 话术库已生成且有 ready 条目 | 骨架轮播为空 | 警告，可继续（建议先生成） |
| 音色 / LLM / TTS 凭据 | 无声或无法生成 | 阻断（说清去哪配） |
| 语音可用性 | 配了但可能不通 | 展示**上次测试发音成功的时间**（存配置），超过 24 小时提示重测 |
| 评论接入（连接器） | 收不到真实评论 | 警告，可模拟 |
| 推流配置 | 只出声不推流（伴侣模式可用） | 警告 |

### 配置态与运行态的分界

开播后场次配置是否即时生效，按"是否改变结构"分：

- **结构性变更**（换人设、换形式、换剧本、重生成话术库）→ **下一场生效**；运行中改了只提示"已保存，下次开播生效"
- **运行态热调整**（音量、BGM、切场景、插话、修订未播话术、启停单个触发器）→ **即时生效**（已有）

### 下播与归档

下播时：停 Agent → 池内心条目归档 → 生成场次摘要（已有）→ 展示本场改写清单供采纳（§5.5）→ 该场运行记录关联 `plan_id` 进数据中心，可横向对比同一场次多次开播的效果。


## 8.7 崩溃与恢复

**约束前提**：一台机器同一时间**只支持一场直播**（单 Agent + 单池的架构决定；多平台并行是后续话题）。

每次开播记一条运行记录：

```
live_runs   id, plan_id, started_at, ended_at,
            stop_reason(normal|crash|panic), last_scene_idx, played_count
```

- 正常下播：写 `ended_at` + `stop_reason=normal`
- 应用崩溃/被强杀：记录停在"未结束"状态
- 下次启动：检测到未结束的运行 → 提示「上次运行异常结束（场次：xxx，播到第 N 场景、已播 M 条），是否继续本场次？」→ 继续则加载场次并从第 N 场景接着播；否则归档
- 池内心条目一律归档（已有行为，播放上下文已失效）

## 9. 分期

| 阶段 | 内容 | 验收 |
|---|---|---|
| P1 | 场次绑知识库 + 生成配置 + **生成 Agent（工具循环：检索/读文件/结构化查询）** + 审阅表（含来源） + 批量预合成 | 一个场次能生成出可用的话术库并全部就绪，来源可追溯 |
| P2 | 轮播方案（场景顺序/变体轮换/循环）+ 直播台切方案 | 开播后骨架按方案轮播，不重复同一条 |
| P3 | 跳转规则（时间/事件/agent/人工）+ 场景面板 | 四种跳转都生效且不打断当前播报 |
| P4 | 闸门（长度/敏感词/价格来源校验） | 构造违规内容能被拦截并留痕 |
| P5 | 中途改写与底稿沉淀（§5.5）：池内行内编辑、复盘列表、采纳/丢弃、溯源 | 现场改写只在本次生效；复盘采纳后底稿更新 |
| P6 | 场次 = 开播单元（§8.5）：plan 绑人设/形式/知识库/话术库/轮播方案，加载与预检，结构变更下一场生效 | 选场次即就位，开播不需要其它页面手动配置 |
| P7 | 评论批处理（§5.7）+ 话术库治理（§5.8）：批窗口配置、合并去重、变体上限与跨场次弱轮换 | 一批评论一次 LLM；变体不膨胀、跨场次不重序列 |
| P8 | 崩溃恢复（§8.7）+ 平台/推流下沉场次 + BGM 列表 + 直答缓存（§5.9） | 崩溃后可续播；不同场次推不同账号 |
| P9 | 模型与语音服务抽象（docs/09）：端口 + 注册表 + manifest 驱动 UI + 本地模型适配 | 加一家服务商只加一个适配器文件；本地 LLM/TTS 可用 |
