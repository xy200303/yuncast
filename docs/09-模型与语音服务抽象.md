# 09 · 模型与语音服务抽象（Provider Ports）

> 状态：待评审 · 2026-10-11
> 目标：**加一家模型/语音服务 = 新增一个适配器文件**，不改主流程、不改设置页；并把"本地模型"作为一等公民而非特例。

## 1. 现状问题

| 位置 | 现状 | 问题 |
|---|---|---|
| LLM | 配置里存 `provider/model/baseUrl/apiKey`，实际经 pi-agent 调用 | 本地模型（Ollama/vLLM/LM Studio）没有明确入口 |
| 语音合成 | `TtsService` 里 `if (provider === 'bailian') … else 火山` | 每加一家要改服务类与设置页两组字段 |
| 实时语音 | 独立服务，协议位待核对 | 与语音合成的关系靠调用方判断 |
| 音色克隆 | 只在火山实现里 | 百炼/本地克隆没有统一入口 |

## 2. 端口定义

### 2.1 语音合成

```ts
interface TtsProvider {
  id: string                    // 'volcano' | 'bailian' | 'local-http' | …
  label: string
  capabilities: {
    streaming: boolean          // 支持流式（边合成边出）
    clone: boolean              // 支持音色克隆
    instruction: boolean        // 支持语气指令
    formats: ('mp3' | 'wav' | 'pcm')[]
    sampleRates: number[]
    /** 音色与模型的配对约束（如某模型只能用某系列音色） */
    voiceModelRule?: string
  }
  /** 配置字段清单——设置页据此渲染表单，无需为每家改 UI */
  configFields: FieldSpec[]
  /** 校验配置是否齐备（缺什么用中文说清） */
  validate(cfg: ProviderConfig): { ok: boolean; missing: string[] }
  /** 非流式：合成到文件 */
  synthesize(req: SynthRequest): Promise<SynthResult>
  /** 流式（capabilities.streaming 为真时实现） */
  synthesizeStream?(req: SynthRequest): AsyncGenerator<PcmChunk>
  /** 克隆（capabilities.clone 为真时实现） */
  cloneVoice?(req: CloneRequest): Promise<CloneHandle>
  queryClone?(handle: CloneHandle): Promise<CloneStatus>
  listVoices?(): Promise<VoiceInfo[]>
}
```

`FieldSpec` 描述一个配置项：`{ key, label, type: 'text'|'password'|'number'|'select'|'switch', placeholder?, help?, options?, default?, secret? }`。**这是解耦的关键**：新服务商的自有参数（如百炼的 workspaceId、某云的区域）由它自己的 manifest 声明，设置页通用渲染。

### 2.2 大模型

```ts
interface LlmProvider {
  id: string                    // 'deepseek' | 'qwen' | 'doubao' | 'local-openai' | …
  label: string
  capabilities: { tools: boolean; vision: boolean; streaming: boolean; contextWindow?: number }
  configFields: FieldSpec[]
  /** 产出 pi-agent 可用的模型描述（pi-ai 的 OpenAI 兼容通道） */
  toModelConfig(cfg: ProviderConfig): { baseUrl: string; apiKey: string; model: string; api: 'openai-completions' }
}
```

**本地 LLM 的落地点就在这**：`local-openai` 适配器把 baseUrl 指向本机推理服务（Ollama `http://127.0.0.1:11434/v1`、vLLM、LM Studio 都是 OpenAI 兼容），几乎零代码——pi-ai 本就支持 OpenAI 兼容端点。

### 2.3 实时语音

`RealtimeTtsProvider` 与语音合成同构，只是必须实现 `synthesizeStream`（双向 WS），配置字段里含 WS 端点与业务空间。百炼、火山各一个实现。

## 3. 注册表与目录

```
src/main/services/providers/
  registry.ts                 统一注册表：getTtsProvider(id) / listTtsProviders() / listLlmProviders()
  llm/
    piCloud.ts                现有云端（DeepSeek/通义/豆包/Kimi/智谱）→ 一个适配器覆盖
    localOpenAi.ts            本地 OpenAI 兼容（Ollama / vLLM / LM Studio）
  tts/
    volcano.ts                火山（含克隆）
    bailianTts.ts             百炼 Qwen-TTS（含 SSE 流式、端点多系列路由）
    localHttp.ts              本地 TTS 服务（见 §4）
  realtime/
    bailianRealtime.ts        百炼实时语音（WS，协议待核对）
```

**约定**：注册表只在 `registry.ts` 里 import 各适配器；业务代码（池、Agent、语音库）只依赖端口类型，不 import 具体适配器。

## 4. 本地模型怎么接（不引入 Python 依赖到主应用）

本地 TTS（CosyVoice2 / GPT-SoVITS / IndexTTS）几乎都是 Python 推理。**不要把它们内联进 Electron**（打包体积、环境脆弱、升级耦合），而是：

```
本地推理服务（用户自己跑，或将来我们提供的启动器）
        ▲  HTTP（约定一套最简协议）
        │  POST /tts   { text, voice, format, sampleRate }   → 音频或 PCM 流
        │  GET  /voices                                       → 可用音色
        │  POST /clone { audio, name }                        → 复刻（可选）
   localHttp.ts 适配器（主应用侧）
```

好处：模型升级与主应用解耦；用户可以用官方仓库/一键包；我们只在需要时提供一个轻量启动器（PyInstaller，P10+ 再考虑）。

**本地 LLM 同理**：OpenAI 兼容端点即可（Ollama 一行配置）。

## 5. UI 由 manifest 驱动（解耦的回报）

设置页不再写死"火山/百炼两组字段"，而是：

```
读 listTtsProviders() → 渲染服务商下拉（label）
选中后按该 provider 的 configFields 渲染表单
按 capabilities 决定功能开关的可用性：
   streaming=false → 「实时合成」开关禁用并说明原因
   clone=false     → 音色库「新建音色」提示该服务商不支持克隆
   instruction=false → 语气指令字段隐藏
```

**收益**：加一家服务商 = 加一个适配器文件，UI 自动出现，测试只需覆盖适配器本身。

## 6. 配置结构迁移

```
现在： tts: { provider: 'bailian', apiKey, model, baseUrl, voiceId, workspaceId, instruction, format, sampleRate, realtime, ... }
改为： tts: { providerId: 'bailian', params: { ... }, voiceId, instruction, format, sampleRate, realtime }
       llm: { providerId: 'deepseek', params: { ... }, model }
       realtime: { providerId: 'bailian', params: { wsUrl }, ... }
```

- `params` 是 `Record<string, string | number | boolean>`，键由各 provider 的 manifest 声明
- **旧配置自动迁移**：读到旧字段（apiKey/model/baseUrl/workspaceId…）时按 provider 映射进 `params`，迁移后写回；迁移逻辑集中一处，配单测
- 密钥字段由 manifest 的 `secret: true` 声明 → 进 `SECRET_KEYS` 加密清单（不再手工维护路径列表）

## 7. 落地顺序（新增 P9）

| 阶段 | 内容 | 验收 |
|---|---|---|
| P9-1 | 定义端口与注册表；把现有火山/百炼包装成适配器（行为不变，先不搬配置） | 现有功能零回归 |
| P9-2 | 配置结构迁移（providerId + params）+ 旧配置自动迁移 + 单测 | 旧配置文件可无缝升级 |
| P9-3 | 设置页改 manifest 驱动；能力声明控制开关可用性 | 加第三个 provider 时设置页零改动 |
| P9-4 | `localOpenAi`（本地 LLM）与 `localHttp`（本地 TTS）适配器 | 用 Ollama + 任意本地 TTS 服务跑通一场 |
| P9-5 | 实时语音纳入注册表 | 与语音合成同一套注册/配置/能力机制 |
| P10 | 其它端口：OutputSink（含虚拟声卡）/ Retriever（含外部知识 MCP）/ Guard（含云端审核）/ 存储仓储 / AudioProcessor | 每项都有≥2 个实现或有外部变体 |


## 9. 其它值得抽象的耦合点（总览）

### 判定原则（避免过度设计）

抽象有成本（多一层间接、多一份心智负担），**触发条件是"第二个实现已可见"**：

- ✅ 值得抽：已有两个实现，或**外部变体可预见**（平台差异、云/本地之分、第三方服务）
- ❌ 不值得抽：只有一个实现且看不到第二个（那就等它出现再抽，YAGNI）

按这条原则过一遍全系统，除模型与语音（§1-8）外，还有五处值得抽、一处要做能力声明。

### 9.1 输出通道 OutputSink —— 优先级：高

| 项 | 内容 |
|---|---|
| 现状 | `StreamService` 里按 `mode: 'direct' \| 'companion'` 分支（FFmpeg 直推 vs 只出声） |
| 为什么抽 | 声音进直播间的方式只会变多：伴侣只出声、RTMP 直推、**虚拟声卡**（给 OBS/其它软件用）、未来云推流/多平台同时推 |
| 抽象形态 | `OutputSink { id, label, capabilities: { video, audioOnly, multiTarget }, start/stop/pushAudio(pcm)/stats() }`；实现：`companion`（纯出声，走系统音频）、`rtmpDirect`（现有 FFmpeg）、`virtualDevice`（虚拟声卡，后续）、`recording`（本地录制，调试用） |
| 收益 | 支持"声音进 OBS 再统一推流"这类部署；场次级选择输出通道（07 §8.5 里"平台/推流下沉场次"正好落在这） |

### 9.2 知识检索 Retriever —— 优先级：高

| 项 | 内容 |
|---|---|
| 现状 | `KnowledgeService` 里写死关键词 LIKE 检索 |
| 为什么抽 | ① 企业客户的资料在自己的系统里（ERP/商品中台），需要**外部知识服务**；② 检索质量升级路径明确：关键词 → 向量 → 混合 |
| 抽象形态 | `Retriever { id, capabilities: { vector, external }, search(query, topK): Hit[] }`；实现：`localKeyword`（现有）、`localVector`（后续，需 embedding 模型）、`mcpKnowledge`（**第三方用 MCP 提供知识，与连接器模式对称**） |
| 收益 | 知识库来源可插拔：本地资料包 / 客户自己的服务 / 云端；`search_knowledge` 工具只依赖端口 |

### 9.3 合规过滤 Guard —— 优先级：高

| 项 | 内容 |
|---|---|
| 现状 | 护栏散落：`check_price` 在工具层、价格护栏在回复服务、敏感词暂无统一实现 |
| 为什么抽 | 平台审核只会更严，且**可能要接官方/第三方内容安全 API**（阿里云内容安全、火山内容审核）；不同场次/平台的尺度也不同 |
| 抽象形态 | `Guard { id, check(text, ctx): { ok, reason?, sanitized? } }`，可组合（链式）；实现：`localRules`（长度/敏感词/价格来源）、`cloudContentSafety`（后续）、`platformRules`（按平台差异） |
| 收益 | 07 §6 的闸门有了统一落点；换审核服务不改业务代码；拦截原因可直接进事件时间线 |

### 9.4 平台动作的能力声明 —— 优先级：中

| 项 | 内容 |
|---|---|
| 现状 | CompanionBridge 只有概念预留，没有端口 |
| 抽象形态 | 连接器在 MCP `initialize` 的 `instructions`/能力里**声明它支持哪些动作**（上屏素材、发福袋、查房间数据…），主应用据此启用/禁用界面按钮 |
| 收益 | 抖音支持上屏、B站支持别的东西，主应用按能力自适应；不会"点了按钮发现平台不支持" |
| 备注 | 与 09 §5 的"能力声明驱动 UI"同一套思路，复用到平台侧 |

### 9.5 存储与记忆 —— 优先级：中

| 项 | 内容 |
|---|---|
| 现状 | 业务代码直接调 `StorageService` 的具体方法（speechUpdate / personaList …） |
| 为什么抽 | ① 未来多设备同步、云端备份需要换实现；② 让主流程只依赖"仓储接口"，测试可换内存实现 |
| 抽象形态 | 按聚合分 Repository：`SpeechRepository` / `PlanRepository` / `KnowledgeRepository` / `MemoryRepository`；实现 `sqlite*`（现有）、`memory*`（测试） |
| 记忆的额外收益 | `MemoryStore` 抽象后，画像可以演进为 结构化 + 向量记忆（老粉的语义检索），不影响主播工具面 |
| 备注 | 这条不急——单机 SQLite 现在够用，属于"顺手收口"，可在 P9 迁移时一起做 |

### 9.6 音频后处理 AudioProcessor —— 优先级：中

| 项 | 内容 |
|---|---|
| 现状 | 重采样（线性插值）、帧对齐等散在代码里手写 |
| 为什么抽 | 接本地 TTS 时经常要重采样/降噪/变速（CosyVoice 输出 24k、某些服务 16k）；统一走一处便于换实现（ffmpeg / 本地算法 / WebAudio） |
| 抽象形态 | `AudioProcessor { resample(pcm, from, to), normalize(pcm), process(pcm, opts) }` |

### 9.7 明确**不**抽的（写下来免得以后纠结）

| 项 | 为什么不做 |
|---|---|
| 插件/扩展系统 | 没有第三方要写插件的可见需求；连接器 + MCP 已经覆盖扩展场景 |
| 文生图 / 多模态生成 | 尚未进入产品范围 |
| 通知（微信/邮件告警） | 等真有运营需求时再加，一个 Notifier 端口即可 |
| UI 组件抽象层 | 已用 shadcn，再包一层是纯负担 |

### 9.8 抽象清单与优先级（汇总）

| 优先级 | 抽象 | 触发条件 |
|---|---|---|
| 高 | 模型与语音（§1-8） | 已触发（要加服务商/本地模型） |
| 高 | 输出通道 OutputSink | 已触发（多平台、虚拟声卡需求可见） |
| 高 | 知识检索 Retriever | 已触发（外部知识服务、向量检索路径明确） |
| 高 | 合规过滤 Guard | 已触发（审核要求） |
| 中 | 平台动作能力声明 | 与连接器能力声明一起做 |
| 中 | 存储仓储 / 记忆 | 顺手收口，随 P9 迁移一起 |
| 中 | 音频后处理 | 接本地 TTS 时一并做 |
| — | 插件/文生图/通知 | 不做（等需求） |


### 9.9 工具注册表与阶段权限（ToolRegistry）

工具本身也是需要抽象的资源——它跨阶段、跨角色复用，且权限不同：

```
ToolRegistry.register({
  id: 'fetch_url',
  label: '抓取网页',
  scopes: ['generate'],            // 只在生成阶段可用（直播阶段禁用）
  params: Type.Object({ url: Type.String() }),
  execute: async (...) => ...,
  /** 安全策略由 Guard 复核（见 9.3） */
})
```

- **按阶段注入**：三个作用域，各自独立的工具集（清单见 07 §4.1 / §4.4 / §8.8）：

| 作用域 | 典型工具 | 说明 |
|---|---|---|
| `live` | say / insert_next / revise_item / advance_scene / goto_scene / set_voice … | 直播运行态；**不含资产写入与联网** |
| `generate` | search_knowledge / read_document / fetch_url / save_utterances | 话术生成；可联网、不能进池 |
| `asset` | create_product / create_script / create_persona / create_plan … | 资产编辑（设置助手）；**不含删除工具**，直播中禁用 |

- **按角色注入**：多 agent 时代（副播/客服）各自只拿到相关的工具
- **与 9.4 的能力声明同源**：连接器声明"支持哪些平台动作"、服务商声明"支持哪些能力"、工具声明"在哪些阶段可用"——同一套思路，避免"调用了不该在这个阶段出现的工具"
- **本地模型场景**：无联网能力时，`fetch_url` / `search_web` 自动从注入列表里剔除（按 capabilities 决定），生成退化为纯本地知识

## 10. 与既有设计的关系

- 池（01 §3.2）只依赖 `TtsProvider` 端口——**换服务商不影响池、轮播、闸门、话术库**
- 语音库克隆流程只依赖 `cloneVoice/queryClone` 端口——火山、百炼、本地模型各自实现
- 音色优先级（07 §8.5 四层）不变：场次 > 角色 > 人设 > provider 默认
- 能力声明让"选了不支持的服务商"从运行时报错变成**配置时就禁用**，这是体验上的重要改进
