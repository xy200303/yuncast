# 05 · 平台接入方案与审核调研

> 状态：已定稿 · 2026-10-11
> 问题：一个软件内置全平台接入，还是解耦为「主应用 + 每平台连接器」？
> 上游：04-平台连接器架构（本文是其调研依据与决策记录）

## 1. 结论先行

**解耦（方案 B）**，理由不是工程洁癖，而是审核风险结构决定的：单体方案下，抖音的提案评审会看见整个 AI 直播软件；解耦后平台看到的只是一个数据工具。

## 2. 各平台互动能力调研（2026-10-11 核实）

| 平台 | 评论/弹幕获取 | 接入方式 | 审核要求 | 风险 |
|---|---|---|---|---|
| **抖音** | ✅ PipeSDK 推送（评论/点赞/礼物/粉丝团/关注，含观众画像字段） | 开放平台 → 直播小玩法 → 互动插件；伴侣以 `--pipeName` 启动插件 exe，C++ SDK | **提案评审制**：先交《互动工具提案》评审通过才能开发，再提审上架；有官方设计规范；Electron 接入方案官方"待补充" | 审核最严；且抖音规则**禁止无人直播**（见 §4 红线） |
| **B站** | ✅ 官方 API（WS 推送弹幕/礼物/进房 + HTTP 项目心跳） | [哔哩哔哩直播开放平台](https://open-live.bilibili.com/) 入驻，审核 1-3 个工作日 | 文档完善、审核相对宽松；注意 [2026-06 起互动玩法旧 API 逐步停服，新接入走官方 API](https://open-live.bilibili.com/document/eba8e2e1-847d-e908-2e5c-7a1ec7d9266f)；[管理规范](https://openhome.bilibili.com/agreement/management-protocol)禁止以 UP 主名义擅发内容 | 低-中 |
| **快手** | ✅ 开放平台有[直播弹幕玩法基础能力](https://docs.qingque.cn/d/home/eZQD5kc0s4EA3C-XlYKi-9_-M)（送礼/评论/点赞推送） | 快手开放平台入驻，企业资质或个人实名认证，接口权限分级 | 认证门槛+权限分级；服务端回调形态为主 | 中 |
| **视频号** | ❌ 无公开弹幕/评论 API | — | 官方未开放，[微信开放社区明确无公开接口](https://developers.weixin.qq.com/community/minihome/doc/0000e485bd09109062e4f34fe6b400) | 不做官方接入 |
| **推流（各平台通用）** | — | RTMP 推流码 | 推流码开播是各平台公开能力 | 低 |

推流侧天然平台无关（RTMP 推流码），平台差异全部集中在**互动数据获取**——这正好印证了把互动接入抽出去的划分是对的。

## 3. 方案对比

### 方案 A：单体（全平台 SDK 塞进主应用）

| 维度 | 结果 |
|---|---|
| 审核 | 抖音提案评审会看到整个 AI 直播软件，AI 无人直播敏感性 → 大概率被拒或要求整改 |
| 依赖 | pipe-sdk（C++ 原生）+ B站 WS 签名 + 快手回调，三套异构栈进同一个安装包 |
| 演进 | 任一平台规则/API 变动（如 B站 2026 停旧 API）都要全应用发版 |
| 用户 | 一次安装 ✅，但 B站用户被迫装着抖音的原生 SDK |

### 方案 B：解耦连接器（主应用 + 每平台连接器）

| 维度 | 结果 |
|---|---|
| 审核 | 平台只见连接器（数据工具），AI 主程序在审核视野外 |
| 依赖 | 主应用零平台 SDK；连接器各自独立打包分发 |
| 演进 | 平台变动只更新对应连接器；主应用协议稳定 |
| 生态 | 协议公开，第三方采集器（哪怕野路子）按协议即可接入 |
| 用户 | 多一步装连接器 ❌（用「首次配置向导」缓解） |

**决策：B。** 抖音连接器按 04 §4.2 包装为「直播数据助手」；B站连接器走官方 API（无需包装，审核宽松）；快手连接器走开放平台弹幕玩法；视频号不支持。

## 4. 合规红线（比技术更重要）

1. **抖音禁止无人直播**：我们的定位必须是「**助播**」——真人主播在场在场控，AI 负责话术与互动辅助。产品文案、提案、演示都不能出现"无人直播""全自动直播带货"字样。这条也反向约束 Agent Anchor 的功能设计：保留并强化真人接管/急停的显性存在
2. **不以主播名义代发内容**：各平台规范都禁止第三方擅自动用主播账号发评论/弹幕（[B站管理规范](https://openhome.bilibili.com/agreement/management-protocol) 明确）。我们只生成语音，不代发文字——当前架构已满足，保持
3. **数据最小化**：连接器采集的观众数据（openid、画像字段）只在本机处理，不上传任何服务器（我们没有服务端，天然满足）
4. 连接器上架后如果平台规则变动（如要求 AI 辅助声明），以连接器侧调整应对，主应用不受影响

## 5. 连接器路线图

| 优先级 | 连接器 | 依据 |
|---|---|---|
| P0 | 抖音「直播数据助手」（pipe-sdk 已有实证封装） | 主战场 |
| P1 | B站（官方 API，无原生依赖，纯 TS 可实现） | 审核快，验证协议设计 |
| P2 | 快手（开放平台弹幕玩法） | 需资质认证 |
| — | 视频号 | 无官方能力，不做 |

每个连接器交付物 = 可送审的独立安装包 + 事件流/动作面服务 + 协议自检工具（`--self-test` 输出协议符合性）。
