# 04 · 平台连接器架构（评论/直播互动的接入方式）

> 状态：已定稿 · 2026-10-10
> 替代方案：旧版 sonic-anchor 的 PipeSDK 直连（native 模块内置）。本文件生效后，主应用不再内置任何平台 SDK。

## 1. 动机

1. **审核隔离**：上架抖音直播伴侣互动工具需要送审 exe。含 AI 语音直播逻辑的应用大概率过不了审；拆出一个行为单纯的「采集器」单独送审，AI 主程序完全不碰平台接口、不在审核视野内。
2. **平台解耦**：主应用不绑定抖音。B 站/快手/视频号各出各的连接器，主应用不变。
3. **第三方生态**：任何人写的采集软件（抓包、OCR、弹幕姬……）只要按协议吐事件即可接入。

## 2. 形态

```
┌────────────┐   ┌────────────┐   ┌────────────┐
│ 抖音连接器   │   │ B站连接器   │   │ 第三方采集器 │   ← 独立小程序，各自送审/分发
│ (pipe-sdk) │   │            │   │ (他们的事)   │
└─────┬──────┘   └─────┬──────┘   └─────┬──────┘
      │ 事件流（WS/SSE, NDJSON）          │
      └────────────────┼────────────────┘
                       ▼
              ┌─────────────────┐
              │  Agent Anchor    │
              │ ConnectorClient  │ → EventBus（comment.new / viewer.join / gift.received …）
              └─────────────────┘
      ▲ 动作面（MCP server，低频工具调用）
      └──── 连接器同时是 MCP server：get_room_stats / send_gift_thanks / 未来上架商品
```

连接器 = 独立运行的小程序，**单一协议：MCP**（v2 修订，原为 WS+NDJSON 事件面 + MCP 动作面双协议）。

修订理由：MCP 底层是 JSON-RPC 2.0，本就支持服务端主动通知（notifications），事件流无需另立协议；统一后一条连接、一个端口、一个 SDK，且连接器天然成为标准 MCP server，任何 MCP 客户端（pi-agent、Claude、第三方 agent）插上即用。

| 面 | 实现 | 用途 | 特征 |
|---|---|---|---|
| 事件面 | MCP notification `notifications/live_event`（Streamable HTTP 的 SSE 通道推送） | 评论/进场/礼物/点赞/分享 → 消费方 | 高频、只读、服务器主动推 |
| 动作面 | MCP tools（127.0.0.1 + Bearer Token） | 查房间状态、上屏素材、出站互动动作 | 低频、请求响应、可审计 |

角色：连接器是 **MCP Server**（能力提供方），主应用是 **MCP Client**。事件类型与主应用 `EventRegistry` 共享同一套命名（`comment.new` / `viewer.join` / `gift.received` / `like.burst` / `viewer.follow` / `viewer.share`），payload schema 文档化公开。连接器绑定 127.0.0.1，不暴露局域网。

## 3. 主应用侧的改动（很小）

- `ConnectorService` 为 MCP client（@modelcontextprotocol/sdk）：连接连接器（默认 `http://127.0.0.1:8102/mcp`），订阅 `notifications/live_event` → 原样注入 EventBus；断线自动重连、状态上报状态栏「评论接入」徽章
- `CommentSimulator` 保留，定位为「内置假连接器」——开发/演示/无连接器时用，走同一条 EventBus 路径
- 出站动作经同一 MCP 连接调连接器工具（CompanionBridge 概念并入 ConnectorService，不再单独预留）
- 主应用代码里**不出现任何平台 SDK 依赖**

## 4. 连接器侧（独立项目，后续再做）

### 4.1 抖音 PipeSDK 调研结论（2026-10-10 核实，官方文档）

- 接入路径：抖音开放平台 → 创建「直播小玩法」→ 选**互动插件**类型 → 提交工具创意提案 → 提案评审通过 → 开发 → 提审上架。有官方《互动工具设计规范》和提案模板
- 技术形态：直播伴侣以 `--pipeName=xxx --maxChannels=6` 启动插件 exe，C++ PipeSDK 经管道通信；Electron 接入方案官方文档标注"待补充"（旧仓库的 native/pipe-sdk node-gyp 封装就是干这个的，可直接挪用）
- **事件能力与我们的事件模型天然对齐**：订阅 `OPEN_LIVE_DATA` 后推送混合数组，msg_type 1=点赞 / 2=评论 / 3=礼物 / 4=粉丝团变更 / 5=关注变更，字段含昵称、加密 openid、头像、内容、荣誉等级、是否关注主播、粉丝团等级
- 主动查询 API：`getOpenGiftPools`（礼物列表）、`getOpenRoomData`（房间总点赞数）
- 生命周期事件：`OPEN_WIN_FOCUS`（置顶面板）/ `OPEN_WIN_CLOSE`（退出进程）/ `OPEN_MEDIA_SOURCE_DELETED`
- 上屏能力（素材通道推送音视频，≤6 通道、单通道 ≤1920×1080）数据助手用不上，不申请

映射表（PipeSDK → 我们的事件协议）：

| msg_type_str | 我们的 type |
|---|---|
| live_comment | comment.new |
| live_like | like.burst（聚合后） |
| live_gift | gift.received |
| live_fansclub（加团/升级） | viewer.follow 级别事件 |
| live_follow | viewer.follow |

### 4.2 产品包装策略：直播数据助手

连接器不做成"裸采集转发器"，而是一个**真实可用的直播数据工具**——这既是产品定位，也是审核友好形态（所有功能都是真功能，不是摆设）：

- **主功能（面向主播）**：评论墙（实时滚动/关键词高亮）、互动数据看板（点赞趋势/礼物统计/进场人数/粉丝团变动）、直播记录导出
- **附属能力（文档化但不吆喝）**：本地开放接口（WS 事件流 + MCP 动作面），面向"高级用户和开发者"，放在设置里作为一个正常功能开关
- 提审提案按「直播数据助手」写：素材图、功能清单、使用场景全部围绕数据看板——它本来就是真的
- 名不与 Agent Anchor 产生任何品牌关联，独立名称、独立仓库、独立分发

这样做的好处是双重的：审核看到的是功能单纯的数据工具；用户得到的也是一个即使不接 AI 也有用的东西。注意把握分寸：不夸大、不伪造功能，所有申报的能力都真实存在——包装的是定位，不是功能。
